# Processor agreements register

Section 40 paragraph 2 of the Personal Data Protection Act B.E. 2562 requires a
**written agreement** between BIRSA, as controller, and each processor that
handles personal data on BIRSA's behalf. The agreement has to set out what the
processor may and may not do with the data, and it is what section 28's
cross-border transfer analysis in the privacy notice actually relies on: not an
adequacy decision (the PDPC has not made one for the United States), but the
appropriate safeguards a data processing agreement puts in place under section
29 paragraph 3.

This document lists every processor recorded in `content/privacy/register.ts`
and the state of the agreement with each one. It is generated by hand from that
file, not by code, because signing an agreement is not something a build script
can do. Whenever a processor is added to or removed from the register, update
this list to match.

**Every row below is currently outstanding.** Signing a data processing
agreement is a decision and an action for the BIRSA committee. Nothing in this
codebase can create one, sign one, or make one true by being written down. This
document exists so the gap is visible and trackable, not so it looks solved.

## Notes on the two rows that aren't a normal processor relationship

**OpenStreetMap** doesn't receive anything BIRSA sends it. A visitor's browser
loads map tiles directly from OpenStreetMap's servers, which is a normal part
of how a web map works and is disclosed in the privacy notice as a cross-border
transfer of the visitor's IP address, not as BIRSA instructing OpenStreetMap to
process data on its behalf. It is listed here for completeness, but it likely
does not need a section 40 agreement in the way the others do, because BIRSA is
not the one sending it data. Worth a second opinion from whoever signs the
others, not a decision to make silently by leaving it off this list.

**Google Forms** is different again: BIRSA doesn't control what those forms
collect, doesn't receive the data itself, and can't delete an individual
response on a visitor's behalf. That's arguably not a controller-processor
relationship under BIRSA's control at all, since BIRSA is not the one
determining the purpose and means of that processing, the club running the
form is (or Google, or both). This needs the committee to actually look at
what each embedded Google Form asks for, club by club, and decide whether
BIRSA is a joint controller, a processor's customer once removed, or has no
section 40 relationship with Google at all. Until that's done, the honest
position is "outstanding and not yet even scoped," which is worse than
outstanding-but-scoped, so it's flagged separately here.

## What "an agreement in place" needs to cover, once BIRSA gets there

When the committee does sign these, each agreement (or, more practically for
Resend and Vercel, accepting their standard Data Processing Addendum, which
both providers publish) should confirm:

- The processor only processes BIRSA's data on BIRSA's documented
  instructions.
- The processor keeps the data confidential and applies appropriate security
  measures.
- The processor doesn't engage a sub-processor without telling BIRSA.
- The processor helps BIRSA respond to data-subject rights requests and
  breach notifications within the timeframes BIRSA itself has to meet
  (thirty days for a rights request, seventy-two hours to know enough to
  report a breach; see `docs/pdpa/breach-response.md`).
- The processor deletes or returns the data when the relationship ends.

## Who needs to do what

This is a BIRSA committee action, not a code change:

1. Locate Resend's and Vercel's standard Data Processing Addendum (both
   providers publish one publicly for exactly this purpose) and have whoever
   holds BIRSA's account with each provider accept it.
2. Decide BIRSA's position on Google Forms, as above, and record the decision
   here.
3. Come back to this document and change "Outstanding" to the date the
   agreement was accepted, for each row, as it happens. A partially-updated
   table is still more honest than deleting this section once it's
   inconvenient to look at.
